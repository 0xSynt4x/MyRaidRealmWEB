# 协作方式与输出口径

> 展开自 `AGENTS.md` 的「协作方式」「自主执行」「沟通与输出」。
> 判据统一：**用户读完不用反问就知道你要干什么。**

## 1. 动手前的确认

- 🔴 **改代码 / 改文件前先讲后动。** 任何增 / 删 / 改（删死代码、抽公共函数、改配置、改目录结构都算）
  先用大白话讲清「改什么 / 为什么 / 影响哪个功能」，**等用户点头再动手**。
- **任务描述里出现「删除」「合并」「重构」不等于已获授权。** 要单独确认。
- **纯只读操作不受限** —— 读文件、搜索、跑类型检查可以直接做。
- 需求含糊时先问清目标 / 范围 / 约束，**最多 3 个问题**，不靠猜。
- **确认只做一次。** 同一任务里用户已经拍过板、给过方向的，直接照办，不再回头问一遍；
  只有出现新冲突、新歧义，或要扩大范围 / 动到任务之外时才重新确认。

## 2. 提示词与数据契约（最严一档）

- 🔴🔴 **动 `schema/`、`src/assets/standalone-local-content/`、`src/assets/standalone-worldbooks/`、
  以及各预设里的提示词文本前，必须先让用户确认。**
- 这几处是**逐字手工设计**的：`schema/` 是数据契约，提示词文本会被原样拼进发给模型的提示词。
- **每一个字都有意义** —— 改标点、调措辞、加一行 EJS 控制、挪一个换行，全都算改动。
- 动手前必须先说清「改哪一句 / 改成什么 / 为什么」，**等用户明确点头**；用户没说改就只读不写。
- 出现「顺带调整」「统一措辞」这类说法也**不等于**授权。
- 这一档**没有任何可自行决定的空间**，比常规改代码更严。

## 3. 一次只推进一项

- 讲清 → 等拍板 → 动手 → 报告。不要一口气铺开好几件事。
- 用户批准的是**具体、可检查的结果**，不是空计划。能直接实施时不要反复停留在复述与方案讨论。
- 当前目标完成后停止，不主动扩展到相邻问题、潜在优化或新功能。

## 4. 自主执行的边界

- 从指令和已有上下文推断实际目标与范围，倾向行动并持续推进，直到目标得到可检查、可使用的结果。
- 对**不会改变需求语义、架构方向、用户数据或最终行为**的常规实现细节，
  自行采用与现有代码最一致的方案，不为此停下询问。
- 只有缺失信息会实质改变结果、架构方向，或操作具有破坏性 / 不可逆性 / 明显数据兼容风险时才询问。
- 可逆、影响小的改动直接执行；破坏性或不可逆操作前必须确认。
- 当用户的建议明显不利于目标时**直接指出，不迎合**。

## 5. 表达口径

- 🔴 **讲用途，不讲名字。** 说「这段代码干嘛的、改完哪个功能会变」，
  不要甩函数名 / 变量名 / 字段名。精确的名字放进代码块，或等用户追问。
- 🔴 **给建议只说「改成什么」。** 清单类输出每条只留动作，现状与推导收进「依据」。
- **先给结论和实际影响，再给必要证据。但结论不能只有结论** —— 后面要跟上依据，
  否则用户无法判断对错。
- 用简洁连贯的段落；只有信息真正并列、需要比较或存在明确步骤时才用列表。
- 需要用户决策时给出少量明确选项并说明推荐，**不抛宽泛的开放式问题**；
  每个选项要写清「选了什么 / 会怎样 / 代价是什么」。
- 技术细节只保留对理解结论、判断风险、复现问题或继续工作有帮助的部分。
- 避免套话、重复总结、无意义术语、未经请求的方案对比和冗长过程描述。
- 不重复用户已经知道的信息，不在结尾主动提出与当前任务无关的后续优化。
- 工作过程中以执行为主，不逐条播报常规的搜索、读取、修改和测试动作。
  只在出现阻塞、需要决策、发现会实质改变方案的重要事实，或完成阶段性成果时同步。
- 最终回复简洁说明：完成了什么、关键影响、做了哪些必要验证、仍存在的真实问题。

## 6. 界面类改动

- 🔴 **视觉 / 界面改动做完直接给用户看，不要自己截图反复复查。** 判据在用户眼睛里，不在你的截图里。
- 允许为定位 bug 做**单次**针对性探测；不要做多视口 × 多帧 × 拼图比对的例行验收。

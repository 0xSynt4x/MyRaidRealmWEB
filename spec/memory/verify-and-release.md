# 验证、提交与发布

> 展开自 `AGENTS.md` 的「测试与验证」「协作方式」中的提交条款。
> 发布流程的完整步骤见 [`../10-workflow-and-verification.md`](../10-workflow-and-verification.md) 与技能 `deploy-online`。

## 1. 验证范围

- 验证范围必须与改动的规模、影响范围和风险相称。
- 优先跑最相关、最小范围的检查（类型检查 / 单测 / 关键路径）。
- 对可逆、低影响、与现有模式高度一致的小改动，不主动编写没有验证价值的新测试。
- 对跨模块数据流、状态同步、存档、提示词链路等高耦合修改，**必须验证直接受影响的关键路径**。
- 已有检查通过且没有新的具体疑点后，停止扩大或重复测试。
- 验证失败时先按失败信息定位原因，**不要立刻扩大为全项目排查**。
- 不主动修复与当前任务无关的既有失败；确认无关后简要记录即可。

## 2. 判据

- 🔴 **「CI 绿」不等于「测试全过」。** 判据是日志里的**通过条数与汇总行**，不是退出码。
- 提交前本地跑齐 `typecheck → test → lint → build`。

## 3. 提交纪律

- 🔴 **工作区改动不提交、不推送。** 除非用户明确要求发布，否则不要 `git commit` / `git push`，
  也不要问「要不要提交」。
- 🔴 **对外发布一律用 `MyRaidRealm` 这类对外名称，不得出现内部目录名。**
- 🔴 动 git 之前先重建代码知识图谱（详见 `.workbuddy-ai/memory/MEMORY.md` 与技能 `deploy-online`）。

## 4. Changelog 约定

- 🔴🔴 **一旦提交，就必须同步补一条 `CHANGELOG.md`。** 完整约定见 `CONTRIBUTING.md` 的「Changelog 约定」。
- 改代码与写 changelog 在同一个工作区里一起改，**不许事后攒**。
- 一条对应一次提交；同一天的提交归在同一个日期小节（`## YYYY-MM-DD`）。
- 标题写成「提交标题」（不带短哈希）。
- merge 也要留一条；关键处带上实测数据。
- 提交前自查：`CHANGELOG.md` 里的条目数应等于 `git rev-list --count HEAD` 的提交数。
- ⚠️ 这条曾经只写在 `CONTRIBUTING.md` 里而从未执行，事后一次性补了 19 条历史提交 ——
  逐个翻提交信息、对 diff 的代价，远大于当时顺手写。
